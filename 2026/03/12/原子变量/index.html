原子变量

发表于2026-03-12|更新于2026-03-13|多线程
|浏览量:

( 原子操作与内存模型/序/屏障 （Atomic operation & Memory model）

众所周知，想要高性能的解决并发问题，使用无锁数据结构会是一个很好的选择。无锁（Lock-free）等于高性能，这种说法虽然十分不严谨，但这种观点却是一个比较普遍的观点。一种更好的说法可能是：使用更小粒度，更底层的锁，往往会有更好的性能表现。

​ ps:无锁数据结构是一种在多线程编程中用于提高性能和避免复杂锁问题的数据结构。它允许多个线程并发访问和修改数据，而不需要使用传统的锁机制。无 锁数据结构的核心思想是通过原子操作来保证数据的一致性和线程的安全

原子操作是无锁（Lock-free）算法的核心，但提到原子操作的同时，必须要关注内存模型(内存序/内存屏障/内存栅栏）。内存模型存在两个层级，一个是编程语言提供的抽象模型（C++ 提供了众多 memory_model ），另一个是体系结构硬件层级，如 X86 的 TSO （Total Store Order）模型。

原子操作

原子操作是什么？

  • 原子操作是被保证以单独一个事务/事件被执行的操作，在该操作执行中不可被打断。
  • 其他线程，可以看到原子操作执行之前的系统状态，或者看到原子操作完全执行结束后的系统状态，但不能看到原子操作执行中的系统状态。（All done or nothing/要么全做要么不做）。
  • 在底层，原子操作是一些特殊的硬件指令，若是硬件不支持是没有办法实现多线程的原子操作的。

一个例子：我们期望两个线程执行完毕后x=2。

X 可能会等于 1 吗？答案是会的。

对于这个操作，整个过程并不是原子的，即另一个线程可能看到操作执行的中间状态。

这是典型的 load-modify-store 操作，我们期望这整个过程都要一起完成，一整个操作是原子的。

引入原子操作

C++11中引入了原子操作。

现在，语言保证了 x 最终会保证 x = 2。

使用方法

C11 中定义了一个 atomic 类型，用于表示原子类型的变量。常见的原子变量类型包括 atomic_int、atomic_bool、atomic_char 等。

内存顺序约束

通过上面的 API 函数我们可以看出，在调用 atomic 类提供的 API 函数的时候，需要指定原子顺序，在 C++11 给我们提供的 API 中使用枚举用作执行原子操作的函数的实参，以指定如何同步不同线程上的其他操作。

定义如下:

  • memory_order_relaxed， 这是最宽松的规则，它对编译器和 CPU 不做任何限制，可以乱序
  • memory_order_release 释放，设定内存屏障 (Memory barrier)，保证它之前的操作永远在它之前，但是它后面的操作可能被重排到它前面
  • memory_order_acquire 获取 , 设定内存屏障，保证在它之后的访问永远在它之后，但是它之前的操作却有可能被重排到它后面，往往和 Release 在不同线程中联合使用
  • memory_order_consume：改进版的 memory_order_acquire ，开销更小
  • memory_order_acq_rel，它是 Acquire 和 Release 的结合，同时拥有它们俩提供的保证。比如你要对一个 atomic 自增 1，同时希望该操作之前和之后的读取或写入操作不会被重新排序
  • memory_order_seq_cst 顺序一致性， memory_order_seq_cst 就像是 memory_order_acq_rel 的加强版，它不管原子操作是属于读取还是写入的操作，只要某个线程有用到 memory_order_seq_cst 的原子操作，线程中该 memory_order_seq_cst 操作前的数据操作绝对不会被重新排在该 memory_order_seq_cst 操作之后，且该 memory_order_seq_cst 操作后的数据操作也绝对不会被重新排在 memory_order_seq_cst 操作前。

原子初始化

使用 atomic_init 函数初始化原子变量。

原子读取

使用 atomic_load 函数读取原子变量的值。

原子写入

使用 atomic_store 函数将值写入原子变量。

原子加法和减法

使用 atomic_fetch_add 和 atomic_fetch_sub 进行原子加法和减法操作。

原子比较并交换（CAS）

原子比较并交换（CAS） atomic_compare_exchange_strong 或 atomic_compare_exchange_weak 是原子变量最常用的操作之一。它尝试将一个原子变量的值与预期值进行比较，如果相等，则将其修改为新值。它是原子操作的基础，用于实现锁-free 数据结构和算法。

原子操作的实现方式：

  • 加载：首先加载当前原子变量的值。
  • 比较：比较加载的值与预期值（即传入的参数）是否相等。
  • 交换：如果相等，使用原子交换指令将原子变量的值替换为新的值。
  • 返回：返回原子变量的旧值，并表示是否交换成功。

原子变量 vs 锁

  • 性能：原子操作比锁的性能要好，因为它们避免了线程上下文切换和锁竞争的开销。
  • 复杂性：锁机制相对简单直观，原子操作需要你理解更多的并发控制细节。
  • 应用场景：原子操作适合简单的数值更新，如计数器、标志位等；而锁适用于需要更多复杂逻辑和状态维护的场景。

内存模型

CPU 在向 Cache 写入的时候，会先向 Store Buffer 里写入，Store Buffer 累积一些写入，然后再写到 Cache 。每个 CPU 有属于它自己的 Cache ，这就带来了缓存一致性的问题，CPU 之间通过 MESI 等协议解决这个问题。

对于 Store Buffer 而言，它写到自己的 Cache 就等于写到内存了，其他 CPU 就应该能看见了，至于复杂的一致性问题，交给 MESI.

MESI 协议用于实现缓存一致性，其定义了四种状态“modified”, “exclusive”, “shared”, “invalid”。

一条 Cache line 无非两种状态，空的的或者装着数据的

  • 空的，就对应 “invalid”
  • 装着数据的，又可分为：与其他 CPU 共有的或者我独占的
    • 共有的，就对应 “shared”。当然在这种状态下，我不能写，其他 CPU 也不能写。
    • 我独占的，又可分为：我改过了或者我没进行修改
      • 独占但没修改，就对应 “exclusive”
      • 独占但已经修改了，就对应 “modified”

除了状态外，还定义了一些操作：

  • Read：请求某个地址 Cache line 的数据
  • Read Response：回应 Read 请求，包含这对应的数据
  • Invalidate：要求在其 Cache 中移除某条 Cache line
  • Invalidate Acknowledge：在收到 Invalidate 后，需要回应 Acknowledge
  • Read Invalidate：Read and Invalidate
  • Writeback：将 Cache line 数据写回到某个内存地址

上述操作与状态共同构成了 MESI 的状态机，状态转换的具体过程略。

CPU 在向 Cache 里写入的时候，若是对应 Cache line 不是他独占的状态，就要相其他 CPU 发送 “Invalidate” 消息，表明：（我要向那条 Cache line 写东西了，在你们 Cache 里的那份过期了，你们要用的话，就再来我这里读新的）。

其他 CPU 收到 “Invalidate” 消息，应使自己 Cache 里对应的 Cache line 无效，然后返回“Invalidate Acknowledge” 消息。
但这有一个问题：

  • 对发送方：要等其他 CPU 先无效对应 Cache line 然后返回 “Invalidate Acknowledge”，我才能继续，若是其他 CPU 正忙，我就需要等待。
  • 对接收方，我收到 “Invalidate” ，然后逐出，然后返回“Invalidate Acknowledge” 也占用我的时间，特别是那条 Cache line 我暂时完全没用到，你要求我立刻逐出它然后返回，也占用我的时间。

由此，便引入了 invalidate queue。当接收到 “Invalidate”消息时，把其放入队列，然后立刻返回“Invalidate Acknowledge” 。待时机空闲，我再处理 invalidate queue ，逐出对应 Cache line。此时，双方的效率都提高了，“Invalidate Acknowledge” 相当于一个保证，我会逐出对应的 Cache line，但我不一定立刻就做。

各种内存模型的操作都是在影响这两个器件（Store Buffer ， Invalidate queue）。

Acquire / Release

  • Release: update what we have made to memroy, publish to other threads.

    • 将我们对内存的修改 publish 出去，使其他 thread 可见我们的修改
    • 刷新 Store Buffer ，让其将内容写入到自己的 Cache 里。

  • Acquire: “acquire” memory published by other threads, making it available to us.

    • 从其他 thread 获得其对内存的修改，使他们的修改对我们可见
    • 处理 Invalidate queue 中的消息，逐出对应 Cache line，当需要时，从其他 CPU 获取新的（“Read”）。

此外，acquire/release 对于指令重排也存在限制。

  • release: 当前线程中的读或写不能被重排到此存储后

    • 即 release 上面的读写操作不能被重排到 release 之后
    • sfence

  • acquire: 当前线程中读或写不能被重排到此加载前。

    • 即 acquire 下面的读写操作不能被重排到 acquire 之前
    • lfence

对指令重排的限制，即是编译器层面的（不做这样的优化），也是 CPU 层面的（依靠 x86 指令 lfence sfence 等）。

acq_rel

二者也可以结合在一起使用，即 memory_order_acq_rel，既是 acquire 操作，又是 release 操作。对于指令重排也是如此，上面的不能排到下面，且下面的也不能排到上面。即刷新 Store Buffer，又刷新 Invalidate Queue。对应 x86 汇编指令 mfence。

Consume

std:memory_order_consume 是对 acquire/release 内存模型的进一步细化，它仅限制依赖变量的顺序。

假设 n 和 m 都是普通的共享变量，最初设置为0。

  • 这里，Thread 1 先修改 n 和 m，然后通过 p 发布指向 n 的指针。

  • 因为 acquire 与 release 配对，Thread 2 的加载操作会同步 Thread 1 的存储，即 Thread 1 中在 release 之前的所有写（① 和 ②）都对 Thread 2 可见。

  • 因此 t 指向 n，*t 是 1，且 m 也是 1。第一个断言通过。

  • consume 语义只保证与加载操作有数据依赖的变量同步。这里，t 的值依赖于 p，而 p 指向 n，所以 *t 依赖于 p。因此 Thread 1 中对 n 的修改（①）对 Thread 3 可见。

  • 但是 m 与 p 没有直接或间接的数据依赖（m 的修改不依赖于 p 的值），所以 consume 不保证 m 的更新对 Thread 3 可见。因此 m 可能还是旧值 0，断言可能失败。

Thread 3 的断言可能会失败，是因为 p 和 m 之间不再有依赖关系，因此在 consume 下，这些值不需要同步。这是对 PowerPC 和 ARM 的指针加载默认内存排序的模拟。(可能还有一些 MIPs 目标)。两个线程都会看到 n == 1 的正确值，因为它被用于存储表达式中，即 n 与 p 是有关联的，是依赖的。

真正的区别可以归结为，为了同步，硬件需要刷新多少状态。由于 consume 操作可能因此执行得更快，知道自己在做什么的人可以把它用于性能关键的应用。

Relaxed

对于内存操作同步顺序没有任何要求。

Sequentially-consistent

顺序一致性是最强的约束，也是 C++ 默认的内存序。

顺序一致性 memory_order_seq_cst = memory_order_acq_rel + 单独全序（single total order）.

这里的单独全序指：所有线程以同一顺序观测到所有修改。

请看这个例子：

是否会出现 r1==1, r2==0 并且 r3==2, r4==0 的情况？

答案是：可能。但是，如果换成 memory_order_seq_cst 就不会出现这种结果。

store 操作可能在全局可见之前，被一些 therad 先看到。

我们通常认为 load 是从 L1d 进行，但是当有 Store Buffer 的时候不一定如此，load 也可能从 Store Buffer 载入（Store-to-load forwarding, SLF）。它甚至允许从没出现在 L1d 的数据从 Store Buffer 载入。

Store buffer 是由同一个 core 的两个 thread 共用的（SB属于OOO的一部分，为属于同1c的2t共有），如果允许一个 thread 窥探同属一个 core 的另一个 thread 在 store buffer 里的内容，就会出现它先于全局其他 thread 看到修改的内容。

但这个问题，在 X86 不能复现，在 ARM 也不能复现，在 POWER 可能复现，语言提供的内存模型和硬件平台实际的内存模型可能存在区别，硬件本身就有更强的内存模型，编程语言没法让他变得更弱。
